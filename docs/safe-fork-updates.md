# 个人 fork 的备份更新

本分支只从 `NewUserNIKO/dsh-purge-upstream` 的 `codex/reliability-fixes` 分支更新。该分支目前承载定制修复，`master` 和继承的旧标签不作为更新目标。以后迁移分支需要同时调整更新策略和安装元数据；不会自动退回原作者或 npm 的包。

## 更新过程

两个面板共用同一更新器，点击更新后会：

1. 把分支解析为一个完整提交 SHA。下载、Git 更新、profile 安装地址和版本记录均使用它，即使远端分支在过程中移动，也不会安装另一份内容。
2. 检查包名、版本、fork 策略标记、完整随包文件及公开入口，拒绝符号链接和安装生命周期脚本。旧构建没有本策略标记时会被拒绝。
3. 检查全部目标，拒绝嵌套目录和不完整的 profile 安装记录。Git 安装必须没有已跟踪修改，只允许快进，并拒绝覆盖冲突的未跟踪/忽略文件；不会因为 Git 失败就改走 ZIP 强制覆盖。
4. 备份受影响文件和更新记录，再更新安装。Git 保留现有分支名称；归档安装保留随包清单之外的文件。profile 的安装地址固定到此次提交，不手工重写 pnpm 锁文件。
5. 所有文件与状态写入成功后才记为完成。捕获到中途错误时恢复全部目标、profile 和更新记录，并保留备份位置。

版本号可以仍为 `1.1.73`；更新检查会比较 fork 提交。旧的上游通道和标签 pin 不再用于此构建，读取更新状态不会顺手改写这些旧配置。已记录 fork SHA 的归档安装还会通过提交关系检查拒绝远端回退或分叉；首次迁移没有可信记录时，以来源及候选策略校验为准。

## 更新与 Apply 分开

成功提示代表**插件文件已更新**。当前进程可能仍在使用旧模块，更新器不会自动重启、刷新页面或运行新包的 `reapply-cli.js`。在合适的时间手动重新加载插件；需要更新宿主补丁时，再执行 Apply。更新代码本身不会改变启用状态。

演练面板保留运行中智能体的阻止检查。更新期间不要从其他进程修改安装目录；Git 在备份完成后会再次检查本地状态，但本实现不是通用的并发编辑合并工具。

## 备份与错误

备份位于 `$DSH_HOME/dsh-purge/update-backups/update-<时间>-<随机标识>/`，父事务目录使用私有权限。每份包含：

- `journal.json`：来源、目标提交、受影响路径、原存在状态、原 Git HEAD 和事务阶段。
- `entries/`：受影响文件/目录的原始副本；记录原来不存在的路径，失败时删除本次新建项。
- `empty-hooks/`：禁用本地 Git hooks 所用的空目录。

成功和失败的备份都保留；不会自动删除历史备份。备份只覆盖插件资源、相关 profile manifest 和更新状态，不读取整个 DSH home 或凭据文件。Git 获取的对象会留在对象库中，失败恢复的是安装文件、HEAD/索引和更新记录，不清理已下载的 Git 对象。

若回滚自身失败，错误会明确报告“恢复不完整”和备份路径；不要把它当作成功。保留备份，依据 `journal.json` 的路径和原始存在状态检查恢复。请勿在不了解现场状态时直接删除锁或再次覆盖。

进程被强杀、系统断电或异常退出不属于“捕获到错误后的自动恢复”。下次更新发现 `.update.lock` 或未完成日志时会拒绝继续，避免叠加破坏。需要先核对现场与保留的快照，完成恢复后再处理锁。本实现不承诺跨目录的断电原子性。

没有执行真实 DSH 更新、Apply 或重启。验证与开发均在评审副本进行，本机已安装的禁用插件保持原样。原作者署名与许可证继续保留。
